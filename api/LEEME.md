# API de administraNET (primer tramo)

Backend real sobre el modelo de datos (`modelo/`): sesión y empresa activa, permisos por rol, clientes, proveedores, artículos con listas y precios, y **factura de venta sin ARCA** (comprobante, asiento automático, stock y trazabilidad en una sola transacción). Es un manejador Node `(req, res)` sin framework, para poder montarlo en Netlify Functions, un servidor propio o el de pruebas.

## Cómo se prueba

```
npm run test:api     # 33 pruebas contra la base real del modelo (PGlite) y un servidor HTTP en un puerto libre
npm run api:dev      # servidor de desarrollo con datos de ejemplo; imprime un token por persona
```

`api:dev` se niega a arrancar con `NODE_ENV=production`. Los datos viven en memoria.

## Cómo se identifica a la persona

1. El front obtiene un JWT del proveedor de identidad (Supabase Auth) y lo manda en `Authorization: Bearer`.
2. `auth.mjs` lo verifica: HS256 con el algoritmo fijado (no acepta `none` ni otro), firma en tiempo constante, `exp`, `nbf`, `aud`, `iss`.
3. Con el `sub` se busca a la persona en `usuario.auth_sub` (`fn_autenticar`). La primera vez se vincula por **email verificado** y una sola vez. Las personas dadas de baja no entran.
4. `X-Empresa-Id` elige la empresa activa; `fn_contexto_empresa` devuelve el rol y los permisos **solo** si la persona tiene vínculo con esa empresa. Una empresa ajena es 403.
5. Cada consulta corre con `set_config('app.estudio_id'|'app.empresa_id'|'app.usuario_id')` y el rol `app_usuario`: el aislamiento por empresa lo impone la base (RLS), no el código de la API.

Roles base (`fn_roles_base`): Administrador, Contador, Auxiliar, Consulta.

## Reglas que conviene recordar

- **Compras**: se carga lo que dice el papel (letra A/B/C/M, punto de venta y número **del proveedor**, fecha, renglones, percepciones) **y el total**. El servidor calcula y **solo carga si el total coincide** (1 centavo de tolerancia); el cálculo previo muestra la diferencia. El número de un proveedor no se repite (ni el de una factura anulada). **A/M a una empresa responsable inscripta**: IVA discriminado, crédito fiscal y libro de IVA compras; **B, C** (y A/M a quien no es RI): el IVA no se discrimina, no hay crédito y todo va al costo (se carga el precio final). Los renglones con artículo toman su tratamiento de IVA y su cuenta; los libres llevan descripción y, si se quiere, una cuenta de gasto. La mercadería con control de stock **ingresa** al depósito (con varios, hay que elegir cuál) con el costo neto de cada ingreso, y el costo del artículo pasa a ser el de la última compra (**último costo**: el parámetro de costeo por empresa todavía no se usa); se avisa si cambia más de 15 %. Los gastos no llevan costo. Anular una compra devuelve el stock a como estaba (si esa mercadería ya se vendió, no se deja), vuelve el costo al de la última compra vigente (no al de una anulada) y no se permite con pagos imputados. Lo de compras y ventas no se mezcla: cada una tiene sus rutas y su permiso, y una venta no se abre ni se anula como compra (ni al revés).
- **Órdenes de compra**: lo que se le pide a un proveedor (es el primer paso de orden de compra → remito de entrada → factura). **No mueven stock, ni generan deuda ni asiento**: solo asientan qué se pidió, a qué precio y para cuándo (entrega prevista opcional; en pesos, sin IVA). Se guardan como **borrador** (se reemplaza o se borra) o ya **emitidas** (no se tocan: se anulan, con motivo, y se carga otra). Numeración propia (`0001-00000001`). El cumplimiento de cada renglón (recibido, facturado, pendiente) sale de `v_documento_pendiente`; una orden con remitos de entrada vigentes o con facturas cargadas no se anula hasta anular eso. Usan los permisos de compras (ver, cargar, anular). Todavía no se cargan los remitos de entrada ni se vincula la factura a la orden: la columna "recibido" se llena cuando existan.
- **Remitos de entrada**: la mercadería que llegó, **contra una orden de compra** (cada renglón apunta al de la orden y no se recibe más de lo que falta: lo impone la base, también si hay dos borradores del mismo renglón) o **suelta**. Al confirmarlo la base ingresa el stock al depósito de cada renglón con control de stock (a su precio como costo del ingreso: movimiento `compra`); los servicios no mueven stock. **No genera deuda ni asiento ni cambia el costo del artículo**: eso lo hace la factura. Lleva el número del remito del proveedor (no se repite para el mismo proveedor, sin distinguir mayúsculas). Borrador (se reemplaza o se borra) o confirmado (solo se anula, con motivo); anular saca el stock, y no se deja si esa mercadería ya no está en el depósito (salvo que la empresa permita stock negativo) ni si hay facturas vinculadas. La orden muestra lo recibido y lo pendiente y lista sus remitos. La factura de compra puede **tomar renglones del remito** (ver abajo).
- **Presupuestos de venta**: la cotización al cliente (presupuesto → pedido → remito de salida → factura). **No mueven ni reservan stock** y no generan cobro ni asiento; asientan qué se ofrece, a quién, a qué precio y hasta cuándo vale (`valido_hasta`: sin indicarlo, 15 días; con `null`, no vence). Borrador (editable y borrable) o emitido (solo se anula, y no mientras haya pedidos vigentes). La **situación** se deriva: vigente, vencido (emitido con la fecha de validez pasada), aceptado en parte o aceptado (según lo pedido en pedidos confirmados). Un presupuesto borrador, anulado o vencido no se pasa a pedido.
- **Factura de venta directo contra un pedido (sin remito)**: en `POST /api/ventas/facturas` (y en `/calcular`) `documento_item_id` también puede ser un renglón de un pedido confirmado del mismo cliente y artículo. Cuando no hay remito **la factura es la entrega**: descuenta el stock (con depósito, que se toma del pedido si no se indica, y con control de stock insuficiente), y toma el precio del pedido si no se indica otro. Lo entregado por remitos más lo facturado directo no puede superar lo pedido (`del pedido solo se pueden facturar N sin remito`); también lo impone la base (`modelo/33_factura_pedido.sql`, que además hace que `v_documento_pendiente` cuente lo facturado directo como entregado y que un remito que ya no cabe no se confirme). El pedido muestra lo entregado, lo facturado y las facturas directas, y no se anula con facturas vigentes. Anular la factura devuelve el stock y lo pendiente al pedido. Pasa solo en ventas: la factura de compra contra una orden sin remito sigue sin soportarse.
- **Pedido contra un presupuesto**: `POST /api/ventas/pedidos` acepta `presupuesto_id` (el cliente es el del presupuesto) y cada renglón lleva `item_origen_id`; artículo, descripción y precio se toman del presupuesto (el precio se puede cambiar). Se puede pedir en partes y no se pide más de lo presupuestado (`solo se pueden pedir N más`; lo impone también la base, sumando los pedidos confirmados del renglón: `modelo/32_presupuesto_pedido.sql`). Un pedido borrador no consume el presupuesto; anular un pedido le devuelve lo pendiente.
- **Pedidos de venta**: lo que pide un cliente (pedido → remito de salida → factura). **No mueven ni reservan stock** y no generan cobro ni asiento; solo asientan qué se pidió, a quién, a qué precio (el indicado o el de la lista del cliente) y para cuándo. Borrador (editable y borrable) o confirmado (solo se anula, y no mientras haya remitos vigentes). Si hoy no alcanza el stock la previa avisa, pero deja confirmar. El cumplimiento (remitado, facturado —a través de los remitos—, pendiente) sale de `v_documento_pendiente`. Solo se piden artículos (no gastos).
- **Remito de salida contra un pedido**: `POST /api/ventas/remitos` acepta `pedido_id` (el cliente es el del pedido) y cada renglón lleva `item_origen_id` (el renglón del pedido; artículo, descripción y precio se toman de él, y el precio se puede cambiar). No se entrega más de lo que falta (`solo falta entregar N`; también lo impone la base al confirmar, sumando los remitos confirmados). Se pueden hacer entregas parciales; el pedido sigue pendiente hasta cubrirse. Anular un remito devuelve el pendiente al pedido.
- **Remitos de salida (ventas)**: la mercadería que se entrega al cliente, contra un pedido o directa. Se guarda como borrador (no mueve stock) o se confirma: **sale del stock del depósito** y el rastro lo cuenta en la categoría `stock`. No se entrega más de lo que hay (por renglón y sumando los renglones del mismo artículo y depósito; también al confirmar un borrador cargado antes), salvo que la empresa permita stock negativo. El precio del renglón es el indicado o el de la lista del cliente, y es el que la factura propone; un renglón sin precio avisa. Anular devuelve la mercadería (`devolucion_venta`) y no se puede mientras haya facturas vigentes del remito. No genera cobro ni asiento: eso lo hace la factura.
- **Factura de venta contra un remito**: en `POST /api/ventas/facturas` (y en `/calcular`) un renglón puede llevar `documento_item_id` en lugar de `articulo_id`. Tiene que ser de un remito de salida confirmado del mismo cliente y del mismo artículo, y no se factura más de lo entregado (sumando las facturas vigentes; también lo impone la base con `fn_verificar_factura_remito`). La factura **toma el precio del remito** (si no se indica otro) y **no vuelve a descontar el stock**: anular la factura tampoco lo toca, el remito vuelve a poder facturarse. Limitación: una nota de crédito sobre una factura de remito no devuelve la mercadería al depósito (se anula el remito, una vez anulada la factura).
- **Factura de compra directo contra una orden (sin remito)**: en `POST /api/compras/facturas` (y en `/calcular`) `documento_item_id` también puede ser un renglón de una orden de compra emitida del mismo proveedor y artículo (o sin artículo, para un flete u otro concepto). Cuando no hay remito **la factura es la recepción**: ingresa el stock (con el depósito de la orden si no se indica otro) y actualiza el costo con el precio de la factura. Lo recibido por remitos más lo facturado directo no puede superar lo pedido (`de la orden solo se pueden facturar N sin remito`); también lo impone la base (`modelo/34_factura_orden.sql`). La orden muestra lo recibido, lo facturado y las facturas directas, y no se anula con facturas vigentes; anular la factura saca el stock y devuelve lo pendiente a la orden. Es el espejo de la factura de venta contra un pedido.
- **Factura contra un remito**: en `POST /api/compras/facturas` un renglón puede llevar `documento_item_id` (el renglón del remito, en lugar de `articulo_id`). Tiene que ser de un remito confirmado del mismo proveedor y del mismo artículo, y no se factura más de lo que llegó (se suma lo ya facturado en facturas vigentes, también lo impone la base). La factura **valoriza y genera la deuda pero no vuelve a ingresar el stock** (la mercadería entró con el remito) y **sí actualiza el costo del artículo con el precio de la factura**, que puede ser distinto del del remito. El remito muestra qué se facturó y en qué facturas; la orden, lo facturado de cada renglón. Anular la factura no toca el stock del remito: el renglón vuelve a poder facturarse; un remito con facturas vigentes no se anula. Una nota de crédito no toma renglones de un remito.
- **Notas de proveedores**: se cargan como una factura (letra, número del proveedor, renglones, total del papel que tiene que coincidir). La **nota de crédito** puede llevar la factura (o nota de débito) que acredita —mismo proveedor, misma letra, confirmada y no posterior a la nota— y se **aplica** a su saldo; sin factura (una bonificación que manda el proveedor) se carga igual, con el aviso, y queda **a favor** hasta que se aplique; si es mayor, lo que sobra queda a favor del proveedor y se aplica después a otra factura. Por renglón puede **devolver mercadería** (sale del depósito; no deja la existencia en negativo salvo que la empresa lo permita). La **nota de débito** es una deuda más: entra en lo pendiente y se paga en una orden de pago. Ninguna toca el costo de los artículos. El libro de IVA compras y el asiento las toman con su signo. Anular una nota devuelve la mercadería, deshace la aplicación y contrarresta el asiento; una factura con notas aplicadas, o una nota de débito con pagos, no se anula hasta anular eso primero.
- **Cobros y pagos**: un cobro (recibo) reparte lo recibido entre facturas de **una** persona —cada imputación no pasa del saldo de la factura— y lo que sobra queda **a cuenta**. Se cobra con efectivo (caja), tarjeta (caja de tarjetas) o transferencia (cuenta bancaria); las **retenciones sufridas** (IVA, Ganancias, Ingresos Brutos con jurisdicción, SUSS) llevan certificado y cuentan como parte de lo cancelado, igual que el descuento por pronto pago. Identidad que impone el servidor: medios + retenciones + descuento = imputado + a cuenta. Un pago es igual pero con retenciones **practicadas** (certificado único por empresa) y **no se gira más de lo que tiene la caja o cuenta**. La fecha no puede ser futura ni tener más de 3 años, y el período contable tiene que estar abierto. Anular exige motivo, que el período de hoy esté abierto y, en un cobro, que la caja o cuenta todavía tenga el dinero; el recibo conserva su número. Anular una factura con cobros imputados no se permite hasta anular antes los cobros.
- **Regímenes de retención**: cada empresa carga los que usa, con el código que le pide su aplicativo (no vienen cargados: no se inventan códigos). Una retención de un cobro o un pago puede llevar `regimen_id`: el régimen tiene que ser del mismo impuesto y no estar dado de baja, fija la jurisdicción (si es de IIBB) y sugiere la alícuota (una alícuota indicada la pisa); el importe sigue siendo el del certificado. Un régimen ya usado no cambia de impuesto. El informe de retenciones muestra régimen y código.
- **Cheques**: un cheque nace dentro de un cobro (de un tercero: banco, número, librador, fecha de emisión y de pago) o de un pago (propio: cuenta bancaria y número; o uno de la cartera, que se **endosa**). Estados de un tercero: en cartera → depositado → acreditado | rechazado, o en cartera → entregado (endoso); propios: emitido → cobrado (debitado). Un cheque **diferido** no se deposita ni se debita antes de su fecha de pago; ninguna fecha puede ser futura ni anterior al último movimiento del cheque, y el período contable tiene que estar abierto. Contablemente, un cheque recibido va a *Valores a depositar* hasta que se acredita (ahí pasa al banco); uno propio va a *Cheques a pagar* hasta que el banco lo debita. Un cheque **rechazado** devuelve la deuda al cliente (entra en su saldo y en la cuenta corriente; se cancela con un cobro a cuenta). Anular un cobro o un pago anula o devuelve a la cartera sus cheques, y no se deja si un cheque ya se acreditó, rechazó o debitó.
- **Planillas fiscales**: `iva-*-detalle` (una fila por comprobante, con el código de tipo de comprobante y de documento de ARCA, moneda, cotización, montos y cantidad de alícuotas), `iva-*-alicuotas` (una fila por comprobante y alícuota, con su código de ARCA) y `percepciones` (sufridas = las de las compras; practicadas = las de las ventas; filtros `origen` e `impuesto`, con resumen por impuesto y jurisdicción). `retenciones` suma el tipo de documento y el régimen (vacío si el pago no lo indicó: hoy las órdenes de pago y los recibos no piden el régimen). Son **planillas de trabajo**, no el archivo de importación de Libro IVA Digital, SIFERE ni SICORE: el diseño de registro de esos archivos no está verificado y se avisa en cada una. Las notas de crédito van en negativo; los comprobantes sin IVA discriminado no tienen fila en la planilla de alícuotas.
- **Alta de ejercicios**: se pueden crear ejercicios anteriores (o cualquier rango de hasta un año que no pise a otro; con sus períodos mensuales, que se acortan en los extremos si no empiezan o terminan a fin de mes) y borrar uno que quedó vacío: sin asientos (ni borradores), comprobantes ni cobros o pagos con fecha adentro, y abierto.
- **Cierre de ejercicio**: lo hace la base en una transacción. Se cierra de a un ejercicio, del más viejo al más nuevo, y solo cuando ya terminó (no se cierra el año en curso). Sin asientos en borrador adentro. El **asiento de cierre** (fechado el último día, `origen_tipo = 'cierre'`) salda cada cuenta de ingreso y egreso contra **Resultados no asignados** (ganancia al haber, pérdida al debe); se cierran **todos** los períodos del ejercicio y, si falta, se crea el ejercicio siguiente. No hay asiento de apertura: los saldos de las cuentas patrimoniales pasan solos porque se derivan de los asientos. Los informes muestran los resultados del año **sin** el asiento de cierre (el estado de resultados, el balance de ese año y los resultados que ve la pantalla de Ejercicios), pero la situación patrimonial al cierre y el año siguiente sí lo incluyen: la ganancia está en Resultados no asignados y los ingresos y egresos arrancan de cero. **Reabrir** anula el asiento de cierre y reabre los períodos, solo del último ejercicio cerrado y mientras el siguiente no tenga movimientos. Un asiento con fecha de un ejercicio cerrado no se contabiliza.
- **Informes**: solo leen y se calculan sobre lo ya registrado; los importes se suman en el servidor con aritmética exacta. Por defecto el período es lo que va del mes (el año para balance, mayor, posición y estados contables). Los **libros de IVA** muestran confirmados y autorizados, con las notas de crédito en negativo, y avisan cuántos comprobantes anulados hay en el período (no figuran). El **balance**, el **mayor** y el **diario** usan solo asientos contabilizados; las cuentas de resultado arrancan de cero con cada ejercicio (si no hay ejercicio cargado, con el año calendario). **Estados contables**: resultados del período y situación patrimonial; como todavía no hay cierre de ejercicio, los resultados acumulados suman todo lo anterior y se controla que activo = pasivo + patrimonio + resultados. **Deuda por antigüedad** es a hoy (vence con `fecha_vto_pago` o, si no tiene, la fecha de la factura) y muestra aparte lo "sin aplicar" (notas de crédito y cobros a cuenta). Cada informe se corta en 5.000 filas: más que eso se acota con fechas. El CSV neutraliza las celdas que una planilla leería como fórmula, salvo los importes negativos.
- **Anular**: solo un comprobante de venta *confirmado* y **sin CAE** (uno autorizado por ARCA no se anula: se corrige con una nota de crédito; la base también lo impide). Conserva su número, la base registra el **contraasiento** con fecha de hoy (hace falta el período de hoy abierto) y el stock que movió vuelve a su lugar (una venta vuelve como devolución). No se anula lo que tiene **cobros imputados** ni **notas aplicadas** (el mensaje dice qué anular antes); una nota de crédito sí, y al anularla se deshace su aplicación y la mercadería que devolvió vuelve a salir (si ya no está, se avisa).
- **Nota de crédito**: sale con la letra de la factura (A→3, B→8, C→13), por el mismo punto de venta, al **mismo precio, descuento, descuento al pie e IVA** de cada renglón; acreditando todo lo que queda da **exactamente** los importes de la factura. Se pueden elegir cantidades (nunca más de lo que queda por acreditar en cada renglón: lo impone la base). Se aplica al saldo de la factura hasta donde alcance; si la factura ya estaba cobrada, el resto queda como **saldo a favor** del cliente. Con `devolver_stock` (por defecto sí) la mercadería vuelve al depósito del que salió. Todavía no hay notas por **importe** (bonificaciones sin devolución) ni notas de débito, ni notas de crédito **de proveedores** (se anula la factura, o queda para un próximo paso); tampoco órdenes de pago a proveedores.
- **Trazabilidad**: solo la ven los administradores del estudio (no hay lectura por empresa). Filtros por tipo, resultado, persona, empresa (o "del estudio"), fechas (**en hora argentina**, no la del servidor), texto y código `TR-000123`, y todo lo hecho sobre un registro. El detalle trae el antes y el después, el origen y si la huella **recalculada por la base** coincide con la guardada y enlaza con el evento anterior. El CSV usa los mismos filtros (tope de 20.000 filas), lleva BOM para Excel y **neutraliza las celdas que empiezan con `=`, `+`, `-` o `@`** (inyección de fórmulas). Exportar y verificar **quedan registrados** en la cadena (con el resultado); leer no. La verificación recorre la cadena, tiene un freno (5 por minuto) y puede compararse con la **cabeza guardada por fuera**: es lo único que detecta que se quitaron los últimos eventos. Todavía no hay un resguardo automático de la cabeza (ver "Lo que falta").
- **Stock**: el libro es de solo agregar; un error se corrige con el movimiento contrario. El conteo físico recibe lo CONTADO y registra la diferencia contra el saldo. El saldo negativo se impide con un mensaje con nombres y cantidades (salvo que la empresa lo permita). Con más de un depósito, la factura exige decir de cuál sale cada bien. Todo queda en la trazabilidad (categoría `stock`).
- **Ajuste de precios**: nuevo = precio de la lista base vigente a la fecha × (1 + porcentaje / 100), redondeado al centavo, al peso o a la decena, con aritmética exacta. Rige desde la fecha elegida (no pisa el historial ni lo ya facturado), avisa los que quedan bajo el último costo y se puede simular antes de aplicar. Máximo 5000 artículos por vez.
- **Administración del estudio** (`/api/estudio/*`): la habilita la marca `usuario.admin_estudio`, no un rol; no necesita empresa activa. Nadie se da de baja a sí misma, el estudio nunca se queda sin administrador activo (lo impone la base), el email de quien ya ingresó no se cambia, y dar de baja a una persona le corta el acceso **en el acto** (cada pedido se vuelve a verificar contra la base). Todo cambio queda en la trazabilidad (categoría `seguridad` o `maestros`) con el antes y el después.
- **Invitaciones**: `POST /api/estudio/personas/:id/invitacion`. No corre dentro de una transacción de la base (hay una llamada de red): comprueba, invita y recién después deja constancia (`Invitó a …`, o `Intentó invitar a …` con resultado `fallo`). Solo a personas activas que todavía no ingresaron; **tope de 3 por persona por hora y 50 por estudio por día**, contados en la trazabilidad (valen aunque haya varias copias del servidor). Si el email ya tiene cuenta, responde `ya_tiene_cuenta` en vez de fallar. Los errores del proveedor se traducen: la respuesta de Supabase no se reenvía y el registro interno guarda solo el estado.
- **Alta de un estudio nuevo**: no la hace la aplicación sino quien opera la plataforma: `DATABASE_URL=… npm run estudio:alta -- --nombre … --admin-email … --admin-nombre … --aplicar` (sin `--aplicar` solo verifica los datos).

- **El total nunca viene del cliente**: se calcula en el servidor con la misma aritmética exacta (decimales, sin punto flotante) que `reglas/calculo.mjs`; un campo desconocido en el cuerpo se rechaza.
- **Letra automática**: la elige la condición frente al IVA de la empresa y del cliente (A, B o C); en la C no se discrimina IVA. El cliente se guarda con su condición (RG 5616).
- **Todo o nada**: si falta stock, el período está cerrado o falla el asiento, no queda comprobante, ni número consumido, ni movimiento de stock.
- **Puntos de venta**: hoy solo `interno` y `preimpresa`. Uno electrónico (`ws_factura`) responde 409 `arca_pendiente` hasta conectar ARCA. Sin indicar `punto_venta`, se usa el único que se pueda usar.
- **Idempotencia**: misma clave y mismo pedido → 200 con el mismo comprobante (`repetido: true`); misma clave con otro pedido → 422.
- **Trazabilidad**: cada alta, cambio (con antes y después) y emisión queda en `evento`, en la misma transacción, con la persona y la empresa. Un cambio que no cambia nada no genera evento.
- **Errores**: `{ "error": { "codigo", "mensaje", "campos" } }`; los errores de validación traen todos los campos con problema juntos. Nunca se devuelven trazas ni mensajes internos de la base.
- **Aislamiento**: pedir un id de otra empresa o de otro estudio da 404 (no 403), para no confirmar que existe.
- **Navegador**: CORS solo para los orígenes permitidos; límite de pedidos (429 con `Retry-After`); tope de tamaño (413); `Cache-Control: no-store`.

### Orden para la primera vez

1. **Supabase → Authentication:** desactivar el alta libre ("Allow new users to sign up"), exigir confirmación de email, fijar la lista de URLs de retorno (la del front) y usar claves de firma asimétricas (JWT Signing Keys). Subir el largo mínimo de contraseña a 12 y activar la protección de contraseñas filtradas.
2. **Supabase → API:** quitar `public` de los esquemas expuestos o desactivar la Data API (el sistema no la usa; `35_endurecimiento_supabase.sql` es la segunda barrera, no la única).
3. `DATABASE_URL=… npm run db:migrar` (muestra qué falta) y luego `DATABASE_URL=… npm run db:migrar -- --aplicar`. Usar la conexión **directa** (puerto 5432) para migrar.
4. Dar de alta el estudio con `npm run estudio:alta` (crea el estudio, sus cuatro roles y la primera persona administradora). Esa persona se **invita** en Supabase (Authentication → Users → Invite) con el mismo email; al ingresar por primera vez queda vinculada y desde la pantalla **Estudio** da de alta sus empresas y personas. Cada persona nueva también necesita su cuenta en Supabase con el mismo email (con `SUPABASE_SERVICE_KEY` configurada la invitación se envía desde la pantalla de personas; sin ella, se invita desde el panel de Supabase).
5. Supabase → Authentication → URL Configuration: agregar `URL_APP` a las URLs permitidas y revisar la plantilla del correo de invitación (la dirección del enlace tiene que llevar a la aplicación). La clave de servicio se copia de Project Settings → API Keys ("secret") y va **solo** en el entorno del servidor.
6. Levantar `npm run api:servidor` con las variables de arriba (para la base conviene la conexión del pooler en modo transacción, puerto 6543).
7. Front: `VITE_SUPABASE_URL` y `VITE_SUPABASE_PUBLISHABLE_KEY` (ver `app/.env.example`).

### Qué no se pudo probar acá
Todo esto se verificó contra PGlite y un proveedor de identidad simulado, **no contra un proyecto real de Supabase**: no hay credenciales en esta máquina. Quedan por confirmar en el primer despliegue: que `POST /auth/v1/invite` responda como se espera con la clave de servicio (la simulación se basa en la documentación de Supabase), que al abrir el enlace de invitación la persona llegue con `type=invite` y el front le pida elegir contraseña, que `btree_gist` se cree bien en su esquema de extensiones, que el pooler en modo transacción acepte el patrón (debería: todo es `SET LOCAL`), que el certificado TLS valide y que los correos de invitación y recuperación lleguen con las URLs de retorno correctas.
